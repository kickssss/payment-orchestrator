Rule 1

One txn = change + event

Outbox row commits with the state change. A crash can lose neither.

Rule 2

MySQL is the only truth

Balances, limits, states never live in Redis.

Rule 3

Proof before success

Pay-ins confirm only on bank evidence; the rest goes to humans.

Rule 4

Gate, hold, submit once

Gate before hold; idempotency key; never blind-retry; every non-terminal row has a deadline.

Rule 5

Replays are no-ops

State guards + unique keys make at-least-once delivery safe.

Why delayed sync cannot hurt you

  1. Claim side — search already-ingested transactions at claim time.
  2. Ingest side — every new credit searches open claims by UTR.
  3. Backstop — a 1-minute sweeper escalates anything past deadline to review.

A match must corroborate

  1. direction = credit
  2. account = exactly the account we displayed
  3. amount exactly equal — anything else is mismatch_review
  4. UTR single-use per account — a second claimant goes to review

Payout: admin asks, system picks, money moves once

1
adminRequest

POST /v1/payouts {amount, beneficiary, idempotency_key} → created. Duplicate key = same answer, never a second payment.

2
executorPick an account

tenant AND account balance ≥ amount · window limits. None → rejected with per-account reasons recorded.

3
ledgerGate, then hold

Acquire the bank gate → one txn: FOR UPDATE aggregates → re-verify limits → hold group → held (available −X, held +X). Funds never pinned behind a statement run.

4
connectorSubmit under gate

ok → in_flight · bank rejects → failed (hold back) · timeout → unknown (reconciler owns it).

5
reconcilerSettle or escalate

settled with evidence · failed with evidence (hold back) · no evidence by max age → payout_ambiguous review, hold kept + webhook.

What if no account qualifies

rejected — reasons per account: NO_BALANCE · NO_LIMITS · GATE_BUSY. Admin sees exactly why.

What if a statement is running

Payout waits with backoff until the gate frees. Statements win. The gate is one MySQL row (bank_gates) — no Redis lease to disagree.

What if submission timed out

unknown → status check / statement search by idempotency key. failed only on positive evidence of non-execution; else payout_ambiguous review keeps the hold.

Matching is inline, not evented

At claim time and inside the sync commit — one shared matcher module, corroborating UTR + amount + account. A 1-minute re-match sweep backstops both sides. Events carry webhooks and payout.created only.

Webhooks out are events too

HMAC-SHA256 signed · exponential backoff retries · timestamp replay window · per-tenant endpoint config.

Bank access: serialized, rate-limited, boring

The gate — statement and payout never overlap

Statements win. When in doubt, the payout defers. One MySQL row (bank_gates) is the authority — expired gate = free; a Redis flush changes nothing.

Sync lock

one sync per connection

Crash → TTL expires → another replica takes over. Watermark + UNIQUE (account, bank_txn_id) = no double ingest. Per-tick page/time budget keeps one slow account from stretching the gate.

Rate limiter

token bucket per connection + op

Atomic Lua in Redis, configured per provider. Callers back off — they never hammer the bank.

Writes never blind-retry

reads: backoff + jitter

Payout submissions carry an idempotency key. Timeout → unknown → the reconciler owns the answer.

Balance drift

every Nth sync tick

fetchBalance → snapshot → compare vs the bank_mirror ledger aggregate. Drift beyond tolerance alerts ops — catches what the watermark overlap cannot.

Money & concurrency

verdict: fixable — skeleton right
  1. ledger groups didn't balance → signs fixed + sum-to-zero invariant test
  2. payout saga could wedge → sweep ALL non-terminal states by deadline
  3. guards were prose → conditional UPDATEs + UNIQUE(matched_bank_txn_id) + FOR UPDATE on the bank txn
  4. no pay-in reversal path → storno group + reversed state
  5. duplicate live-UTR claims → UNIQUE(account, active_utr) → utr_reuse review

Simplicity & ops

verdict: fixable — "boring in the best way"
  1. stuck-held payouts → bank query by idempotency key; gate BEFORE hold
  2. gate had no DB-half spec → bank_gates row, single authority
  3. retry/DLQ undefined → 5 attempts → DLQ + alert + admin replay
  4. 7 worker loops → 4 (master sweeper owns deadlines, retries, janitor)
  5. one events stream; processed_events dropped; matching inline
